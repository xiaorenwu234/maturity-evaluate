# 模块一：数据收集与统一知识图谱构建 —— 执行逻辑与流程详解

> 目标：读完本文，你应能完整理解 **数据从哪里来、怎么被采集、采集了什么、图谱如何构建、语义如何增强、最终以什么形态产出**，并能定位每一步对应的源码文件。

本文对应代码包 `src/kg_builder/`，CLI 命令为 `kgb`。

---

## 0. 一句话架构

模块一把「**源代码 / 文档 / 部署 / 运行时**」四类来源，通过一组可插拔采集器归一化成同一套图原语（带证据链的节点与关系），合并进一张**统一系统知识图谱（Unified System Knowledge Graph）**,再由 **LLM 做语义增强**,最后产出 JSON / Mermaid / Cypher,并可一键导入 Neo4j。

这张图谱是模块一的**唯一产物**,也是模块二(评估与问题发现)、模块三(问题修复)**唯一的数据入口**。

### 三条贯穿全局的设计原则

1. **无回退（no fallback）**：宁可不产出,也不产出低置信度的替代品。
   - 某语言的解析器不可用 → **跳过该文件**,不会退化到正则粗扫。
   - 语义增强只由 **LLM** 完成,没有离线启发式兜底;LLM 未配置就**直接报错**,或显式 `--skip-enrichment` 跳过整个增强步骤(这是"可选步骤开关",不是降级)。
2. **证据链优先（provenance-first）**：每个节点/关系都携带一个 `provenance` 列表,记录「这条事实来自哪个来源、哪段原文、置信度多少」。同一逻辑事实可被多来源佐证并**累积合并**,这正是模块二做跨来源一致性/矛盾检测的基础。
3. **确定性 ID + 幂等合并**：节点 ID 由 `类型:命名空间:规范名` 做 SHA1 派生,重复构建得到同样的 ID;不同采集器发现的同一实体自动落到同一节点上合并。

## 1. 顶层执行流程

编排代码:[`pipeline/build_pipeline.py`](../src/kg_builder/pipeline/build_pipeline.py) 的 `BuildPipeline.run()`。

```
                    settings_for(repo, out, config_file=..., **overrides)
                                     │  解析出 BuildSettings（见 §2）
                                     ▼
   ┌──────────────────────── BuildPipeline.run() ────────────────────────┐
   │                                                                      │
   │  1) build_collectors(settings)  -> 四个采集器实例                     │
   │     for c in collectors:                                             │
   │        if not c.is_enabled(): skip                                   │
   │        res = c.collect()   -> CollectorResult(节点+边+provenance+告警)│
   │                                                                      │
   │  2) _merge(results):                                                 │
   │        先把所有 nodes 灌入 KnowledgeGraph（建端点）                    │
   │        再把所有 edges 灌入（按 (src,dst,relation) 合并，证据累积）      │
   │                                                                      │
   │  3) _enrich(graph):                                                  │
   │        if settings.enrich:                                           │
   │            llm = create_llm_client(settings.llm)  # 未配置即抛错      │
   │            SemanticEnricher(llm).enrich(graph)    # LLM-only 语义     │
   │        else: summary = {"skipped": True}                           │
   │                                                                      │
   │  4) _write(graph):                                                   │
   │        save_graph -> *.json（主产物）                                 │
   │        side-car  -> *.mmd(Mermaid) / *.cypher(合法 Cypher)           │
   │                                                                      │
   │  return BuildReport(graph, results, warnings, enrichment)            │
   └──────────────────────────────────────────────────────────────────────┘
                                     │
                                     ▼ （可选，独立子命令）
                    kgb export-neo4j <graph.json>  -> 参数化批量导入实时 Neo4j
```

**顺序很关键**:必须先加节点后加边——`KnowledgeGraph.add_edge` 要求两端节点已存在,否则抛 `KeyError`(合并阶段对缺失端点的边会记 warning 并丢弃)。见 [`knowledge_graph.py`](../src/kg_builder/graph/knowledge_graph.py) L92-L98。

## 2. 配置体系：三层优先级

代码:[`config.py`](../src/kg_builder/config.py)。所有构建参数收敛到一个 `BuildSettings` 树。

**优先级(后者覆盖前者)**:`默认值 < YAML 配置文件 < KGB_* 环境变量 < CLI/关键字覆盖`。
解析入口 `settings_for(repo_path, output_path, config_file=..., **overrides)`(L208)。

配置模型一览:

| 模型 | 关键字段 | 作用 |
|---|---|---|
| `BuildSettings` | `repo_path` / `output_path` / `docs_path`(默认=repo) / `namespace` / `enrich` | 顶层构建开关 |
| `CodeSettings` | `enabled` / `exclude_dirs` / `max_file_bytes`(512KB) | 源代码采集 |
| `DocumentSettings` | `enabled` / `extensions` / `max_file_bytes`(1MB) | 文档采集 |
| `DeploymentSettings` | `enabled=False` / `kubeconfig` / `context` / `namespaces` / `cluster_name` | 部署采集(**当前 stub**) |
| `RuntimeSettings` | `enabled=False` / `prometheus_url` / `trace_backend` | 运行时采集(**当前 stub**) |
| `LLMSettings` | `provider` / `model` / `base_url` / `api_key` / `temperature` / `json_mode` / `max_items_per_call` | 语义增强(**LLM-only**) |

- **环境变量**:前缀 `KGB_`,嵌套键用 `__`,例如 `KGB_LLM__MODEL`、`KGB_CODE__ENABLED=false`、`KGB_LLM__MAX_ITEMS_PER_CALL`。见 `_env_overrides()` L150。此外兼容 `OPENAI_API_KEY / OPENAI_API_BASE / OPENAI_BASE_URL / OPENAI_MODEL` 作为 llm 字段的回退来源(L170-L178)。
- **`enrich`** 是顶层布尔,`True`(默认)会运行 LLM 增强;`False`(CLI `--skip-enrichment`)只构建结构图。
- **LLM 必填校验**:`LLMSettings.require_configured()`(L105)——`enrich=True` 但 `model`/`api_key` 缺失即抛清晰错误,提示去配置文件/env 设置或用 `--skip-enrichment`。**绝不静默降级**。

参考模板:[`config.example.yaml`](../config.example.yaml)。本地私有配置 `config.yaml`/`config.local.yaml` 已加入 `.gitignore`。

## 3. 采集器契约与四个来源

契约代码:[`collectors/base.py`](../src/kg_builder/collectors/base.py);注册:[`collectors/__init__.py`](../src/kg_builder/collectors/__init__.py) 的 `build_collectors()`。

每个采集器读取**一类输入**,产出统一的 `CollectorResult`:

```python
@dataclass
class CollectorResult:
    collector: str
    nodes:    list[KGNode]   # 已带 provenance
    edges:    list[KGEdge]   # 已带 provenance
    metrics:  dict           # 扫描文件数/解析失败数/树-sitter 状态等
```

`BaseCollector` 要求实现 `collect()`,并可用 `is_enabled()` 自我禁用。**所有采集器都产出同样的 KGNode/KGEdge 原语**,这是"代码/文档/部署/运行时事实能落在同一节点、形成跨来源证据链"的根本原因。

|---|---|---|---|---|---|
| **Code** | `collectors/code/code_collector.py` | `source_code` | Module / Function / Service / API / Database / ExternalDependency / Config | CALLS / DEPENDS_ON / EXPOSES / READS / WRITES / CONFIGURED_BY | 完整实现 |
| **Document** | `collectors/document/doc_collector.py` | `document` | Document / Config / Service / API | DEPENDS_ON(documents) / CONFIGURED_BY | 完整实现 |
| **Deployment** | `collectors/deployment/k8s_collector.py` | `deployment` | Deployment / Service | DEPLOYED_AS | **stub**：映射逻辑已写好并测试,真实抓集群的 `_fetch_workloads()` 返回空 |

## 4. 源代码采集器（重点）

文件:[`collectors/code/code_collector.py`](../src/kg_builder/collectors/code/code_collector.py)。内部子模块:

```
collectors/code/
├── languages.py          # 扩展名->语言；Tree-sitter 可用性检测
├── artifact.py           # 语言无关的中间表示 (IR: FileArtifact)
├── extractors/
│   ├── python_extractor.py     # 标准库 ast（Python 主路径，置信度 0.95）
│   ├── treesitter_extractor.py # Tree-sitter（其它语言，置信度 0.9）
│   └── __init__.get_extractor()# 显式选择，无回退
├── frameworks.py         # 启发式：路由/数据库/外部服务/缓存/MQ/配置键
├── static_analysis.py    # SymbolIndex：跨文件把调用点解析成真实 CALLS
└── code_collector.py     # 编排：walk -> extract -> enrich -> resolve -> emit
```

### 4.1 `collect()` 的主循环（L51-L96）

1. **遍历源文件** `_iter_source_files()`:仓库 `rglob("*")` 排序,命中 `exclude_dirs`(node_modules/.git/venv/dist/build/…)即整路径跳过。
2. **识别语言** `detect_language(path)`(`languages.py`):按扩展名映射表(见 4.2);非源文件返回 `None` 直接跳过。
3. **选择解析器** `_resolve_extractor(language,...)`:`get_extractor(language)` 构造失败 → 记一次 warning、缓存 `None`、**跳过该类文件**(不退化)。
4. **读取+体积门槛**:`max_file_bytes`(默认 512KB)以上跳过;读失败记 warning。
5. **抽取 IR**:`extractor.extract(rel, source, module)` → `FileArtifact`;随后 `frameworks.enrich(art, source)` 补路由/资源/配置。
6. 记录 `extractor_kind`(`python` 或 `tree-sitter`),用于 §4.6 的置信度。
7. 全仓库 IR 收齐后:`SymbolIndex.build(artifacts)` 建全局符号表;`_detect_services()` 找服务类;`_emit()` 把 IR+解析出的调用映射成节点/边。

`result.metrics` 会带回:`files_scanned` / `files_skipped_no_parser` / `files_without_symbols`(解析后无符号的可疑文件) / 各语言实际用的解析器类名 / tree-sitter 状态。

### 4.2 支持的语言与解析器（无回退）

- **语言识别表**(`languages.py` `EXT_TO_LANGUAGE`):`.py/.pyi`→python;`.js/.jsx/.mjs`→javascript;`.ts/.tsx`→typescript;`.java`;`.go`;以及 ruby/php/csharp/kotlin/scala/c/cpp/rust 等扩展名可识别。特殊文件名:`Dockerfile`、`Gemfile`、`go.mod`、`pom.xml`。
- **解析器注册**(`extractors/__init__.py` `get_extractor`):
  - `python` → 标准库 `ast` 抽取器(零额外依赖,调用/导入解析最准)。
  - 其它语言(`javascript/typescript/java/go`)→ `TreeSitterExtractor`,**需要**可选依赖 `tree-sitter` + `tree-sitter-language-pack` 且该语言有语法;缺失则 `get_extractor` 抛异常 → 上层**跳过文件**。
  - 无语法配置的语言(如 ruby/c) 直接 `raise ValueError` → 跳过。
  - **不存在正则兜底**(该路径已按"无回退"原则删除)。

### 4.3 中间表示 IR（`artifact.py`）

所有语言解析结果都归一到这套 dataclass,后续静态分析/框架识别/图映射只认 IR,与语言无关:

- `FileArtifact`:`path / language / module` + `classes / functions / calls / imports / routes / resources / configs`。
- `ClassDef`:限定名、基类 `bases`、装饰器、方法名列表。
- `FunctionDef`:限定名 `qualified_name`(module.Class.method 或 module.func)、`class_name`、`decorators`、`params`、`is_async`。
- `CallRef`:**调用点**——`caller_qname`(所属函数)、`callee_name`(文本名,如 `self.repo.save`/`requests.get`)、`args`(字符串/名字提示)。
- `ImportRef`:模块与导入符号。
- `RouteDef`(框架识别产出):`framework / http_method / path / handler_qname`。
- `ResourceRef`(框架识别产出):`category(database|cache|message_queue|external_service) / target / operation(read|write|publish|…) / evidence`。
- `ConfigRef`:`key / default / evidence`。

### 4.4 Python AST 抽取（`python_extractor.py`）

`_ScopeVisitor` 单次遍历一棵 `ast`:
- 维护 `_class_stack` / `_func_stack`,使方法只记一次、每个调用点都归属到**所在函数的限定名**。
- `visit_Import/ImportFrom` → imports;`visit_ClassDef` → classes(含 bases/decorators/methods);`visit_(Async)FunctionDef` → functions;`visit_Call` → calls(`_dotted` 把 `a.b.c` 属性链渲染成文本名,`_string_args` 抓字符串实参供后续识别 URL/连接串)。
- 语法错误 → 返回空 IR(best-effort),不崩整个构建。

Tree-sitter 抽取器同理产出 IR(非 Python 语言)。

### 4.5 框架/资源/配置启发式（`frameworks.py`）

AST 只知道"有个函数、调用了个名字",但不知道 `@app.route("/order/create")` 是 HTTP 接口、`session.query(Order)` 碰了数据库。`enrich()` 补三类语义,**保守、语言标注、可解释**:

- **路由 → API**(`_detect_routes`):
  - 先看函数装饰器 `_parse_decorator_route`(`.get/post/put/delete/patch/route`)。
  - 再扫内联注册:`_PY_ROUTE_RE`(flask/fastapi)、`_JS_ROUTE_RE`(express)、`_JAVA_MAPPING_RE`(spring)、`_GO_ROUTE_RE`(gin/echo);`route` 归一为 `ANY`。`(method,path)` 去重。
- **数据库/缓存/MQ/外部服务**(`_detect_resources`):
  - 由持久化库 import(sqlalchemy/psycopg2/mongo/redis…)推断 DB 目标。
  - 由**调用名 token** 分类:读(`query/select/find/get/…`)、写(`insert/save/add/update/delete/commit/…`)、缓存(`cache/memcached`)、MQ(`publish/kafka/celery/queue/…`)、HTTP(`requests/httpx/axios/grpc/client/…`)。
  - **关键防误判**:DB 读/写只有当**接收者链像持久化对象**(`repo/session/connection/dao/mapper/model/query/…`)且不在黑名单(`os/sys/router/app/request/resp/json/…`)时才成立(`_has_db_receiver`)。
  - URL 主机字面量 `https://host` → external_service;`*Repository/*Dao` 调用 → database。
  - 推断不出具体外部目标时**不臆造** generic 节点(`_infer_external_service` 返回 None)。
- **配置键**(`_detect_configs`):`os.getenv("X")` / `os.environ["X"]`、`settings.X`(Django)、`@Value("${x}")`(Spring)、`viper/config.GetX("k")`(Go)。

> 说明:这一层是**采集期静态启发式**(不是 LLM),对真实项目可能出现少量误标(例如把某些 `*.query()/models` 判成 Database)。它总是带 `source=source_code` 与具体 `evidence` 原文,模块二可按置信度/来源过滤,不影响服务拓扑主干。

### 4.6 静态调用分析（`static_analysis.py`）——把调用点变成 CALLS 边

`SymbolIndex.build()` 汇总全仓的 functions/classes/methods。`resolve(call)` 把文本调用名尽力解析成具体函数/所属类:

1. `self.method()` → 在调用者所属类内查方法。
2. `self.<field>.<method>()` → 用字段名 token 轻量匹配某个类(近似类型推断,`_match_service_by_token` 处理 snake/camel,如 `payment_client`→`PaymentClient`、`payment`→`PaymentService`)。
3. 全限定名精确命中函数;唯一同名裸函数;`Foo(...)` 类实例化;`payment.charge` 这类对象限定调用。
4. 都命不中 → 只保留原始名(不猜边)。

产出 `ResolvedCall(caller_qname, callee_qname, callee_class, raw_name, ...)`,让图谱能表达 **`OrderService --CALLS--> PaymentService`** 这种服务级调用。

### 4.7 映射成节点/边（`code_collector._emit`,L161-L295）

**服务识别**(`_detect_services` L141):类名以 `Service/Controller/Router/Resource/Api/Handler/Manager` 结尾,或类里有带路由装饰器的方法 → 判为可部署 Service。

发射规则(每条都带 `prov(art, line, evidence)`,`source=source_code`,置信度按解析器 `python=0.95 / tree-sitter=0.9`):

| IR 内容 | 节点 | 关系 |
|---|---|---|
| 每个文件 | `Module` | — |
| 服务类 | `Service` | `Module -DEPENDS_ON{contains}-> Service` |
| 函数/方法 | `Function` | 若在服务内:`Service -DEPENDS_ON{owns}-> Function` |
| 路由 | `API`(名 `"{METHOD} {path}"`) | 若 handler 归属服务:`Service -EXPOSES-> API` |
| database/cache 资源 | `Database` | 归属服务:`Service -{READS/WRITES/DEPENDS_ON}-> Database`;否则归到 Module |
| 其它资源(外部/MQ) | `ExternalDependency` | `Service -DEPENDS_ON-> ExternalDependency` |
| 配置键 | `Config` | `Service|Module -CONFIGURED_BY-> Config` |
| 解析出的函数调用 | — | `Function -CALLS-> Function`(去重) |
| 解析出的服务级调用 | — | `Service -CALLS{level:service}-> Service`(去重) |

- **归属服务**用 `_owner_service_of_handler`(处理函数所在类)/`_nearest_service`(资源/配置行号所在方法最接近的服务)启发。
- **去重**:服务级/函数级 CALLS 各用 `(src,dst)` 集合去重,避免同一调用被重复记边。
- **幂等 `_ensure`**:同 `(类型,规范名)` 已存在则**合并 provenance**,不新建节点。

## 5. 文档采集器

文件:[`collectors/document/doc_collector.py`](../src/kg_builder/collectors/document/doc_collector.py)。来源标记 `document`,置信度 **0.8**。它扫两类输入(docs 根默认=repo,受 `exclude_dirs` 与 1MB 体积约束):

- **散文文档** `.md/.markdown/.rst/.txt`(`_handle_text`):
  - 每份产出一个 `Document` 节点(`format/kind=prose/path`)。
  - 正则抽**服务名 token**(`\w+(Service|Controller|Gateway|Client|Manager)`)→ `Service` 节点 + `Document -DEPENDS_ON{documents}-> Service`。
  - 正则抽 **HTTP 路径**(`/a/b/c`)→ `API` 节点(`"ANY {path}"`)。这些可与代码里的同名/同路径事实**跨来源合并或并列**,是模块二发现"文档说的和代码做的不一致"的原料。
- **结构化配置** `.yaml/.yml/.json/.toml/.ini/.properties`(`_handle_config`):
  - 用对应解析器(yaml/json/tomllib/正则 k=v)读取,**递归扁平化**成 `key.subkey` → 值,过滤过泛键(`version/name/enabled/type/kind/metadata/spec`),最多取 500 个 → `Config` 节点(带 `value/source_file`)。
  - 若文件里能识别出服务名(`_service_hint`:文件名或正文),则 `Service -CONFIGURED_BY-> Config`。
  - 解析失败(坏配置)只记 warning,返回空,不影响其它文件。

`Document` 节点本身也进图,`kind` 区分 `prose`/`config`。

## 6. 部署与运行时采集器（当前 stub）

为符合"先不接真实集群/监控"的要求,这两个采集器**默认关闭**(`enabled=False`,CLI `--enable-deployment/--enable-runtime` 可开),但**映射逻辑与证据链已完整写好并有单测**:

## 7. 合并语义（`KnowledgeGraph`,图容器）

文件:[`graph/knowledge_graph.py`](../src/kg_builder/graph/knowledge_graph.py)。它是模块一唯一对外交付物的载体,内部用 `dict` 存 `KGNode/KGEdge`(可选导出 `networkx.MultiDiGraph` 给模块二跑算法)。

`_merge(results)`(`build_pipeline.py` L102):
1. **先节点**:遍历各采集器结果 `graph.add_node(clone)`,同 ID 已存在则**合并**——属性 `setdefault`(先到者保留,不覆盖)、`provenance` 累积去重。
2. **后边**:`graph.add_edge(clone)`,合并键是 `(source, target, relation)`;同一条边的多来源证据累积进 `provenance`。端点缺失的边丢弃并 warning。

因此「代码说有个 `Payment` 服务、部署也说集群里有 `Payment`」会落在**同一节点**上,`sources` 同时含 `source_code` 与 `deployment`,证据链完整。克隆(`_clone_node/_clone_edge`)保证不回改采集器自身结果对象。

`stats()` 给出:`node_count / edge_count / nodes_by_type / relations_by_type / provenance_by_source`——这正是 `kgb inspect` 和构建报告摘要的数据。

## 8. 语义增强（LLM-only）

文件:[`enrichment/semantic_enricher.py`](../src/kg_builder/enrichment/semantic_enricher.py) + [`enrichment/llm_client.py`](../src/kg_builder/enrichment/llm_client.py)。

**只做静态分析和原始来源给不了的"判断类"语义**(这正是模型擅长、规则不擅长的):

| 目标节点 | 让模型判断 | 写入 `attributes.semantic` 的键 |
|---|---|---|
| `Service` | 业务领域、是否**核心业务链路**、一句话职责 | `business_domain / is_core_business / responsibility` |
| `API` | 是否属核心业务链路、一句话摘要 | `is_core_business_link / summary` |
| `Config` | 该键控制什么运行时行为、类别 | `controls / category` |

**做法**:
- 先收集服务级 `CALLS` 的扇入/扇出 + `EXPOSES` 接口,拼成结构化"服务清单"喂给模型(带上下文,而非臆测实现)。
- 按 `max_items_per_call` **分批**(如 25/批),每批一次调用,请求**严格 JSON**:键=实体名(与输入完全一致),值=判断字段。
- **系统提示词**约束:「只依据给的结构信息判断,不臆造实现,严格按 JSON 输出,不加解释」(`_SYSTEM`)。
- 模型没返回对应键 → **跳过该实体,绝不猜**(`if not isinstance(opinion, dict): continue`)。
- 每条模型结论都作为 `Provenance(source=llm, evidence=模型原话, confidence=0.7, detail={method:"llm", model:...})` **附加**到节点上。置信度 0.7 **刻意低于**观测事实(代码 0.95/文档 0.8),便于模块二区分"事实"与"推断"。

**LLM 客户端**(`LangChainLLMClient`):
- 用 `langchain_openai.ChatOpenAI` 指向**任意 OpenAI 兼容端点**(OpenAI / Qwen / DeepSeek / 自建 vLLM 网关,靠 `base_url` 切换)。
- `json_mode=True` 时带 `response_format={"type":"json_object"}`(对 thinking 类模型尤其重要,能约束出干净 JSON)。
- `complete_json()` 解析失败或请求失败 → 抛 `LLMError`(**无静默回退**);`_parse_json_loose` 会尽力从杂乱文本里抠出 JSON 块。
- 工厂 `create_llm_client()` 不配置就 `require_configured()` 抛错——**没有 NullClient**。
- 测试用**依赖注入**一个 `FakeLLM`(`complete_json` 返回预设 dict)来跑通增强逻辑,这是测试替身,不是产品回退。

## 9. 图数据模型（本体 + 节点/边/证据）

文件:[`graph/ontology.py`](../src/kg_builder/graph/ontology.py)、[`graph/model.py`](../src/kg_builder/graph/model.py)。

### 9.1 词表（本体）

- **节点类型 `NodeType`**:`Service / Module / API / Function / Config / Database / Deployment / Metric / Document / ExternalDependency`(中文标签见 `NODE_TYPE_LABELS`)。
- **关系类型 `RelationType`**:`CALLS / DEPENDS_ON / DEPLOYED_AS / CONFIGURED_BY / READS / WRITES / EXPOSES / OBSERVED_BY`(全部有向)。
- **来源类型 `SourceType`**:`source_code / document / deployment / runtime / llm / manual`——驱动证据链。

### 9.2 核心结构

```python
Provenance:  source_type, source_id(文件:行 / cluster/ns/kind/name / semantic://llm),
             evidence(原文片段), confidence(0..1), detail(dict), collected_at(UTC)

KGNode:      id(确定性), type, name, canonical_name, namespace, attributes, provenance[]
             sources => 去重来源集合; add_provenance => 同(来源id+证据)去重并保最高置信度

KGEdge:      source, target, relation, attributes, provenance[]
             key => (source,target,relation) 即合并键
```

- **节点 ID** `make_node_id(type, canonical, ns)`(model.py L32):`type:ns:canonical` 小写做 SHA1 前 12 位 + 可读前缀,例 `Service/PaymentService#a1b2c3d4e5f6`。**确定性 → 重复构建幂等、跨采集器合并**。
- **置信度分层约定**:Python AST 0.95 / Tree-sitter 0.9 / 文档 0.8 / 运行时 0.9 / 部署 1.0 / **LLM 推断 0.7**。

## 10. 序列化与产出

文件:[`graph/serialization.py`](../src/kg_builder/graph/serialization.py)、[`graph/neo4j_import.py`](../src/kg_builder/graph/neo4j_import.py)。

`kgb build` 产出三份(`_write`):
1. **`*.json`(主产物)**:`{schema_version, stats, nodes[], edges[]}`,节点/边各带完整 `attributes` 与 `provenance`。模块二/三消费的就是它(`load_graph` 可原样载回)。
2. **`*.mmd`(Mermaid)**:快速可视化,边数上限 200 截断。
3. **`*.cypher`**:合法、可导入的 Neo4j Cypher——按标签建 `CREATE INDEX ... IF NOT EXISTS`,节点 `MERGE (n:\`Type\` {id}) SET ...`,关系 `MATCH(a),(b) MERGE (a)-[r:\`REL\`]->(b) SET ...`。Neo4j 属性只能是标量/数组,故 `attributes`、`provenance` 存 **JSON 字符串**,`sources` 存字符串数组(证据链仍可 `CONTAINS` 查询)。

**一键导入实时 Neo4j**:`kgb export-neo4j <graph.json>`(见 §11),核心是 `import_graph_to_neo4j()`:
- **参数化 UNWIND 批量**(500/批),不解析文本 Cypher(避免证据里 `;`/引号被误切)。
- 节点按标签分组 `MERGE`;关系按 `(源标签,目标标签,关系类型)` 分组 `MERGE`,命中 id 索引。
- 自动建索引;**幂等**;失败即抛 `Neo4jImportError`(不产生半成品);标签/关系名做标识符正则校验防注入。

## 11. CLI 全流程

文件:[`cli.py`](../src/kg_builder/cli.py)。所有命令建议用 `conda run -n CMMeter kgb ...`。

```bash
# 1) 构建（含 LLM 语义增强，默认开启；用配置文件提供模型）
kgb build <repo> -c config.yaml -o out/kg.json [-n namespace] [--docs-path DIR] [-v]

#    只构建结构、跳过 LLM：
kgb build <repo> --skip-enrichment -o out/kg.structural.json

#    打开 stub 采集器（演示用）：
kgb build <repo> --enable-deployment --enable-runtime

# 2) 查看统计 / 按类型或名字检索节点
kgb inspect out/kg.json [--type Service] [--name Order] [--limit 50]

# 3) 查看某实体的完整证据链（多来源 provenance + 关系）
kgb evidence out/kg.json PaymentService

# 4) 导入本地 Neo4j（幂等 MERGE；密码三来源：--password/env/交互提示；--clear 先清空）
kgb export-neo4j out/kg.json --uri bolt://localhost:7687 --user neo4j [--clear]
```

Python API:`from kg_builder import build`;`build(repo, out, enrich=False)` 或注入 `llm_client=`。

## 13. 设计取舍与已知边界

- **采集期启发式的误差**:`frameworks.py` 的 DB/外部服务识别是静态猜测,真实项目可能少量误标(如把某些方法判成 Database)。缓解:都带 `source=source_code` + `evidence` 原文,可按置信度/来源过滤;不影响服务拓扑主干。后续可将这部分也交给 LLM 或引入更强的类型分析。
- **语言覆盖**:Python 走 AST(最准);JS/TS/Java/Go 需 Tree-sitter 可选依赖+语法;**缺解析器就跳过该文件,绝不正则兜底**(无回退原则)。其它已识别扩展名但无语法的语言同样跳过。
- **部署/运行时**:当前为 stub,数据契约/标签/关系/证据形状已就位,接真实来源只替换 `_fetch_workloads/_fetch_metrics`。
- **语义增强完全依赖 LLM**:未配置模型则构建报错;需要纯结构时用 `--skip-enrichment`(是"跳过可选步骤",不是降级)。
